# Canteen Management System - Backend

## Phase 2: C Backend Foundation

This project is a C-based HTTP API backend for a Canteen Management System. It uses Mongoose (a lightweight C networking library) to handle HTTP requests.

### Project Purpose
To provide a DSA-focused C backend that serves a frontend via HTTP APIs. Currently, business features (like auth, carts, food management) are intentionally **NOT** implemented yet. Only the foundational routing, HTTP server, and configuration layers exist.

### C Backend Architecture
- **Server Wrapper (`server.c`)**: Initializes the Mongoose event manager and listens on a configured port.
- **Router (`router.c`)**: Dispatches incoming URLs and methods to specific handler functions.
- **Config (`config.c`)**: Reads environment variables with sensible defaults.
- **Response (`response.c`)**: Provides reusable helpers for sending standard HTTP status codes and JSON messages.
- **Mongoose**: Used to abstract raw TCP/socket management and HTTP parsing safely.

### Data Models & File Storage (Phase 3)
- **Data Models:** Located in `include/models.h`. Includes C structs for `Student`, `Admin`, `Food`, `Order`, `OrderItem`, and `SalesRecord`.
- **Storage Strategy:** Flat binary files (`.dat`) are used in the `backend/data/` directory.
- **ID Generation:** ID is dynamically generated by counting the existing records in a file. `ID = (filesize / sizeof(struct)) + 1`. This provides instant O(1) lookup speeds because `Offset = (ID - 1) * sizeof(struct)`.
- **Update/Delete Strategy:** Physical deletion is avoided to preserve ID mapping. Instead, structs have an `active` integer flag (1 = active, 0 = inactive).

### Data Structures & Algorithms (Phase 4)
The core DSA logic is implemented completely in C and kept separate from file I/O:
- **Linked List (`dsa/linked_list.c`)**: Used for representing dynamic memory lists like Cart items or parsing order history dynamically. Complexity: O(1) insert at head/tail, O(N) search/delete.
- **Queue (`dsa/queue.c`)**: A strict FIFO (First-In-First-Out) queue. Used for handling admin canteen orders efficiently in the order they were placed. Complexity: O(1) enqueue and dequeue.
- **Stack (`dsa/stack.c`)**: A strict LIFO (Last-In-First-Out) stack. Useful for tracking recent actions, page navigations, or undoing operations. Complexity: O(1) push and pop.
- **Priority Queue (`dsa/priority_queue.c`)**: A sorted queue. Used for priority canteen orders. Complexity: O(N) insertion, O(1) extraction.
- **Searching (`dsa/search.c`)**: Linear Search O(N) for finding food/users by string. Binary Search O(log N) for finding IDs in sorted arrays.
- **Sorting (`dsa/sort.c`)**: Bubble, Selection, and Insertion sorts O(N^2). Used for sorting Food items by price or popularity before responding to the frontend.

### Authentication & Authorization (Phase 5 / 5.1 Hardened)
- **Student Registration & Login**: Routes (`/api/student/register`, `/api/student/login`) mapped to `.dat` file storage.
- **Admin Login**: Seeded by default (`admin@canteen.com` / `admin123`). Log in via `/api/admin/login`.
- **Session Strategy**: In-memory token storage utilizing the `LinkedList` DSA. Sessions reset on server reboot. Tokens are cryptographically generated using native Windows CNG (`BCryptGenRandom`).
- **Authorization**: Middleware intercepts the `Authorization: Bearer <token>` header, verifies the token string via a LinkedList `ll_search`, checks role permissions, and either passes control or returns `401 Unauthorized` / `403 Forbidden`.
- **Password Security**: Password hashing is now abstracted in `auth_crypto.c`. For development, it uses a placeholder salted-hash function. Real PBKDF2/bcrypt can easily be dropped into the interface for production. Temporary plain passwords are securely erased from memory immediately after verification/registration via `crypto_secure_erase()`.
- **Logout**: Route (`/api/auth/logout`) deletes the session node from the linked list, invalidating the token.
- **Dependencies**: Building on Windows now requires linking `bcrypt.lib` (`-lbcrypt`) alongside `ws2_32.lib`.

### Food & Menu Management (Phase 6)
- **Admin Food Endpoints**: `/api/admin/foods` to Add, Update, and Delete (Soft delete).
- **Admin Inventory Endpoints**: `/api/admin/foods/:id/price`, `/api/admin/foods/:id/stock`, `/api/admin/foods/low-stock`, `/api/admin/foods/out-of-stock`.
- **Public Menu Endpoints**: `/api/foods` automatically excludes out-of-stock, manually disabled, or deleted items.
- **DSA Integrations**:
  - **Food Collection**: In-memory `LinkedList` traversed for displaying the menu.
  - **Food Search**: `/api/foods/search?q=...` explicitly uses the `linear_search` from Phase 4 across the food arrays.
  - **Menu Sorting**: `/api/foods?sort=...` explicitly converts the linked list to an array, runs `bubble_sort`, `selection_sort`, or `insertion_sort` depending on the sort criteria, and re-links it into the JSON response.
  - **Stock Traversal**: Simple `LinkedList` traversal checks threshold conditions.

### Cart & Order Processing (Phase 7)
- **Student Cart (`/api/cart`)**: Fully stored in memory utilizing a dedicated `LinkedList` instance per active student session. Carts reset across server restarts. Prevents duplicate entries and ensures requested quantity validates instantly against authoritative Food stock.
- **Order Placement (`/api/orders`)**: Reloads Food stock, snaps current prices, persists an `Order` struct containing up to 20 `OrderItem` structs, dynamically decreases Food stock (`stock -= qty`), and cleans the student's cart memory.
- **Queue System**: Processed Orders enter an in-memory FIFO `Queue` DSA as `ORDER_PENDING`.
- **Admin Order Processing**: `/api/admin/orders/next` performs `dequeue()` to pull the oldest order. The state machine strictly forces `PENDING -> PREPARING -> READY -> COMPLETED`.
- **Queue Persistence Strategy**: While the `Queue` lives entirely in memory, `order_system_init()` automatically iterates `orders.dat` on reboot and re-queues any previously `PENDING` orders, guaranteeing 100% loss-prevention of queued orders.

### Order History & Analytics (Phase 8)
- **Student History & Receipts**: Endpoints `/api/orders/history` (utilizing `LinkedList` traversal), `/api/orders/:id`, and `/api/orders/:id/receipt`. They enforce historical unit-price integrity, ignoring subsequent Admin menu price adjustments.
- **Daily Sales Dashboard**: `/api/admin/sales/daily` runs aggregations directly from the authoritative `.dat` storage into memory arrays, securely finalizing revenue only for `COMPLETED` orders.
- **Popular Food Analytics**: `/api/admin/popular-foods` generates a leaderboard by allocating an array and invoking the Phase 4 `bubble_sort` algorithm to rank items by quantity sold descending.
